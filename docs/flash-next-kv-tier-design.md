# 精度模块与 QSA 主机 KV 执行设计

状态：Flash-Next第一阶段必做内容，替代第一版“dense BF16、全GPU K/V”的假设。量化／驻留选择独立于模型名字；本设计与[主设计](flash-next-design.md)一起交给实现者，不能交给黑盒作者。

## 1. 三个独立选择，不能绑在模型上

文件容器与量化格式分开。当前源是safetensors，不是GGUF；同样的NVFP4／FP8可以有不同容器。文件读取器负责解析编码，量化组件负责权重／scale与算子，模型负责计算结构，KV组件负责历史存储。

| 选择 | 来源／配置 | 解析规则 |
| --- | --- | --- |
| dense权重 | 新公共参数 `--dense-quant auto|bf16|fp8`，Python `dense_quantization`，默认auto | auto遵从每个算子的检查点方案；bf16为显式展开到BF16；fp8为显式选择FP8。不能把auto写成“若Qwen4则FP8” |
| K/V编码 | `--kv-dtype auto|bf16|int8`，Python `kv_dtype`，默认auto | auto保持后端既有原生格式；bf16／int8要求相应codec能力，不根据模型名设置默认 |
| K/V驻留 | `--kv-placement gpu|tiered`，Python `kv_placement`，默认gpu | tiered允许活跃页驻主机；实际放在哪里由当时资源决定，不固定每请求多少GPU页 |
| 专家权重 | 既有检查点元数据及 `--nowag-expert-path` | 保留已有ExpertBanks/provider选择；与dense、KV两个选项正交 |

本任务的交付运行配置显式使用 `--dense-quant fp8 --kv-dtype int8 --kv-placement tiered`，关闭项用bf16／gpu配置对照。它是用户选择的运行配置，不是写进Flash-Next模型类的策略。既有模型省略新参数时行为不变。

CLI可选方案及错误提示从实际的量化方法／codec／驻留能力注册表生成，不能在parser、loader和engine各维护一份硬编码名单。表中列出的是本阶段要实现和验收的注册项；后续NoWAG或其他方法通过同一能力入口接入。

这些配置在启动／转换时解析，本轮不新增运行中热切换精度。tiered模式内部的逐页迁移是正常动态执行，不需要重启或改开关。显式不支持的组合报组件能力错误，不静默改精度／后端；bf16展开已量化权重不等于恢复量化前原始数值。

## 2. 独立量化模块与真实调用方

采用上游QuantConfig／Scheme／Method的职责划分，不整颗搬入全仓重构：

1. 格式读取器提供规范化的源权重描述：逻辑shape、源dtype／量化编码、scale、分片／融合关系。HF／FTW／已有GGUF读入最终提供同一种描述，本阶段不新增Flash-Next GGUF支持。
2. 模型构造只声明实际算子及角色：dense投影、embedding、norm、MoE路由／专家。模型不能含 `if fp8`、`if nowag` 或根据模型名挑精度的forward分支。
3. 公共策略把用户选项、源描述、算子角色／shape、硬件能力解析为一次性的量化计划。注册项按算子与编码能力选择；禁止Hub ID、目录名、`model_type`白名单。
4. 同一计划同时决定权重加载／转换、算子构造、实际字节数和FTW声明。不能加载器量化一份，模型再从独立环境变量猜另一份。
5. 模型forward只调用构造好的投影或MoE；codec只在KV写入／读取边界执行。调度器不读取FP8、INT8或NoWAG格式名称，只消费组件报价和申请结果。

模型注册按architecture找到实现、加载器把权重键对应到算子，是描述模型所必需的映射；禁止的是用这些名字选择精度／驻留或限制公共能力。算子角色由组件声明，策略不得通过路径包含 `qwen`、层号清单或某个文件名来猜角色。

本地已有 `models/quant_linear.py`、`kernel/triton/fp8_pertensor_linear.py`、`moe/expert_banks.py` 和NoWAG provider，先抽取／复用它们。dense方法从当前Linear工厂接入；移除新路径中“expert_quant决定dense精度”的隐式耦合。只实现已有BF16／FP8和当前专家provider的真实调用，不增加无人使用的量化插件层。

最小公共接口是：源读取器输出weight scheme；Linear工厂接收算子描述和已解析scheme并构造现有实现；KV组件接收codec和placement策略。原来需要的数据留在原对象，不为这三步再包装一层引擎。FTW的scheme描述实际写出的张量，不能只复制仍称dense BF16的源配置。

dense选择范围通过算子角色表达，不靠权重路径子串。本次FP8 运行配置选择非路由的dense投影和输出头；embedding、norm、卷积、递推参数及路由自身保持原组件精度。QSA/GDN/残差/PLE的权重名称映射仍属于模型加载适配，它只描述哪项权重属于哪项算子，不决定量化政策。

后续NoWAG接入应增加／接通专家provider及其数值契约，不改decoder、QSA、调度或KV codec。NoWAG需要的输入舍入、normalizer位置、路由权重应用位置由实际专家组件声明，不能向公共入口追加一个模型名。现有模型已确认语义保持；本阶段不宣称新Flash-Next NoWAG产物已经适配或验收。

## 3. Dense FP8 的可关闭实现

本地源的dense是BF16。显式fp8策略使用FP8 E4M3、逐输出行FP32 scale、W8A16：激活保持BF16。复用现有GLM逐行量化函数并移到公共量化模块；旧GLM调用也使用同一函数，不保留复制品。

量化以CPU分块／逐矩阵进行；融合投影连同scale按相同输出行顺序拼接，HC填充行是零值与有效scale。不要求320、48或4这样的真实维度凑成128块。BF16策略直接使用源权重；auto读取源方案。真实源为FP8时bf16策略只解码该权重，不承诺恢复原始BF16模型。

所有Linear，包括输出头的selected入口，都调用同一个已解析方法。W8A16没有输入激活标定scale时，不能为了prefill提速自动改成另一套W8A8数学。FTW转换保存实际FP8编码与scale，并在元数据中说明方案；auto加载该FTW按其声明执行，不依赖转换机的环境变量。

FP8／BF16选择不能改变专家NVFP4／NoWAG选择，也不能暗改KV dtype。数值基线分两层：相同量化权重的算子一致性，以及相对源BF16权重的模型质量变化。

## 4. INT8 KV codec

对QSA实际写入的、已完成norm／RoPE的K和投影后的V，分别按每token、每KV head计算对称scale；不量化QSA压缩索引或GDN状态。

```text
m = max(abs(x[head_dim]))
s = BF16(m / 127)；全零向量使用 s = 1
q = clamp(round_to_nearest_even(x / float32(s)), -127, 127).int8
读取：float32(q) * float32(s)，attention按既有规则累加／输出
```

量化使用最终存储的scale，避免先按一个值量化、再按舍入后的另一个值解码。K／V的scale独立；128/256维内按真实shape归约。fresh尾部与历史都使用同一codec，不能新token直接读BF16、老token才读INT8而隐含另一套比较语义。

- 每token的12层K/V载荷为12288 B；BF16 scale共96 B。scale、载荷和有效长度一起保存、搬运和释放。
- GPU／CPU放置不改变字节，不反复量化；读INT8时在attention kernel中应用scale，不创建整段BF16历史。
- bf16 codec保留同样的页和驻留接口，用作关闭量化的运行路径；不能通过另一套缓存管理器实现。
- 截断／取消／页复用按有效长度掩码；scale也必须属于当前有效数据，不读未初始化或其他请求的尾部。

## 5. 页的有效性与驻留分离

每个逻辑历史页仍有稳定标识和引用。组件内部维护两个独立对象：

- GPU压缩索引页：活跃请求计算需要的完整索引。其容量随历史增长，不能截成top-k窗口。
- K/V载荷：INT8或BF16编码及scale，有GPU位置或已完成的HostStore副本；可以同时有两者，只有有效版本可供读取。

最小状态流：

```text
GPU写入中的尾页 → 完成页 → 正在复制到CPU → CPU副本有效
                                      → GPU载荷可释放，索引仍驻GPU
CPU有效历史 → 本轮选中数据暂存 → attention → 暂存复用
```

GPU写入槽、索引页和请求状态由现有runtime物理块提供，但不再把所有逻辑K/V历史都映射到GPU。新页的索引、写入槽和必要状态共同申请；失败不发布半份页。GPU载荷布局及块粒度由QSA组件报告，不把旧MHA bank价格直接套过来。

已完成页在GPU资源不足时可转主机；优先使用现有可回收容量，再按完成顺序释放有有效CPU副本的载荷。尚未写完或仍在被计算／复制读取的页不释放。逻辑前缀受保护不等于其GPU副本永远不可迁移；迁移必须保留完整有效的主机版本。

每个活跃请求的未完成尾页可以留GPU。暂停时可以将其有效部分保存主机；恢复继续追加时只取得一个可写GPU尾页并恢复其有效前缀，不恢复全部历史。公共前缀仍按完整页共享。

## 6. 活跃主机 KV 的读取

一次QSA层执行：

1. 更新本轮K/V编码和索引，GPU读取完整压缩索引并选出稀疏组。
2. 根据GPU上的页驻留表定位选中的K/V。GPU驻留位置直接读取；主机位置通过已注册内存的设备地址gather到有界GPU暂存。
3. 只取得选中的4-token组和必要因果尾部，连同scale。页是存储／引用单位，不意味着一次命中就传整张64-token页。
4. 同一个attention kernel消费选中数据及scale。暂存按当前物理query行数申请，逐层复用，不为所有12层各留一份完整副本。

索引选择结果留在GPU，不能每层 `.tolist()`／同步回CPU再发复制命令；主机地址表、驻留表和Graph暂存地址在回放期间稳定。采用本项目已用于PLE的pinned-host设备访问机制，新增的是KV gather，不是新的CPU服务线程。

每query暂存上限由QSA选择预算＋一个组的因果尾部决定（此几何不超过2052位置）。多个query可能选不同组，费用按实际执行行数计，不假定共享命中或去重收益。长prefill按索引打分与gather暂存共同约束分块。

批次运行期间持有它会读取的历史及驻留映射，取消／迁移不能提前改写地址或释放HostStore内存。复制完成、映射发布和GPU最后读取事件由原搬运／runtime生命周期串联；不同流不靠全设备同步兜底。

## 7. HostStore、前缀与暂停的接法

沿用 `--prefix-cache-host-gib` 的同一个HostStore，把它的公开说明扩展为冷前缀、暂停副本及tiered模式的活跃K/V总预算。固定PLE表／专家源权重不计入该数据预算，但必须计入整机RAM。0预算不允许偷偷创建第二个主机KV池。

组件向现有HostTier提供三项真实能力：保留已存在的主机历史引用、恢复时安装这些引用的映射、释放引用。已有HostSpan继续承担分裂／共享，不复制出第二份同内容K/V来分别充当“活跃历史”和“冷副本”。GPU-only组件保持原复制行为；公共流程通过能力调用，不能写Qwen名字分支。

prefix／pause包含GPU索引和全部请求状态，以及K/V有效位置的组件句柄。冷命中／恢复时索引及状态回GPU，已存在的K/V仍可留主机。替换逻辑页号和状态槽时同步更新地址映射。当前未完成尾页的GPU恢复费用单独计价。

主机空间不足先淘汰无保护冷数据，不能淘汰唯一有效的活跃K/V。再不足时，将压力交给同一个PauseManager，选择请求暂停并保留输入／已提交输出以重算；不另写QSA请求队列或另一套受害者策略。恢复和重算都继续遵守源请求的输出位置与到达顺序。

新准入须为这段执行必需的GPU和CPU资源取得一致的预留；任何一边失败都撤销本次未提交预留。已经发出的复制／计算保护不当成可立即使用的余量。

## 8. 157K、多用户与专家槽预算

活跃请求的GPU费用包括约随历史线性增长的压缩索引、GDN／附加状态、写入尾页和有界执行暂存；完整原始K/V不要求常驻GPU。主机费用包括尚不能丢弃的历史。单请求可执行范围与逐轮准入同时看两边容量，不根据假定最大并发预占全部数据。

157000 token下，当前INT8＋BF16 scale K/V约1.811 GiB／请求，压缩索引约115 MiB／请求；状态和工作区另计。主机空间不足时不承诺无限历史／并发。合法预算能同时容纳多个这类请求时，验收必须观察到它们共同持有历史并交错推进，不能把全部串行当作多用户支持。

FP8和INT8节省只有真正进入专家分配才算新增槽。启动自动容量读取实际权重／codec／驻留方案报价；显式预算不变时，runtime内部省下的空间仍属于runtime，不能双算到专家。使用同总GPU／CPU约束报告基线和新配置的实际专家槽数。

稀疏选中2048 token的INT8载荷约2 MiB／层／query；12层约24 MiB的主机读取只是量级估算，实际页驻留和因果尾部另计。这些流量与专家搬运共享PCIe。可容纳157K与可接受的交互延迟分别验收，不能宣称主机KV没有带宽成本。

## 9. 对现有共享池的明确扩展

原共享池PR不含QSA或逐轮活跃KV读取。这里新增的是KV组件的双层驻留、codec、稀疏gather及其资源报价，不把它描述成接一个注册项就完成。

复用不变的部分：物理块申请／释放、HostStore／复制完成、请求排队、暂停／恢复／重算、输出提交和取消。必要扩展落在组件能力与资源申请；所有precision和placement选择来自显式配置、检查点和实际能力，调度器不认识模型名字。
