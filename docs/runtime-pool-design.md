# 共享 runtime 池与请求暂停恢复设计

状态：PR #9 已补生产修复与单卡服务验收；当前结果、实际版本及尚未归因的 Graph 启动 OOM 见[收尾报告](runtime-pool-closeout.md)。基线为 `main@732f1ee`。TP、多模态验收按用户决定暂缓，不作为本轮补验前置，也不计为已通过。
工作树：`.worktrees/runtime-pool`，分支 `feat/runtime-pool`。

## 1. 目标和已确认边界

服务面对持续到达、长度和实际并发未知的请求。用户给资源预算，服务根据已经存在的历史和本轮工作决定资源分配；不要求预测实际输出长度、完成时间或未来到达。

| 决策 | 已确认内容 |
|---|---|
| 共享范围 | 目标 KV、GDN 状态、ReplaySSM 请求记录、DFlash 历史、SD 临时状态共用物理 runtime 容量。 |
| 专家池 | 首版保持独立容量，不与 runtime 借还；不改变专家驻留／CPU-GPU 分流策略。 |
| 内存压力 | 支持活跃请求暂停、CPU 卸载与恢复；不仅处理已完成请求的冷前缀。 |
| CPU 不足 | 允许保留已提交输入／输出、释放可重建 GPU 历史，通过重算恢复。 |
| 首版组件 | 全注意力目标KV及已有GDN组件，包括对应self-SD／DFlash、ReplaySSM、batching和冷前缀；没有GDN的受支持目标不强制创建状态池。DFlash的有限窗口必须纳入。目标SWA／DSV4、QSA／DSA等稀疏attention接入及逐轮CPU KV streaming均不纳入本PR，其原路径保留。公共流程按组件角色与能力组织。 |
| 配额接口 | 共享模式只接受 runtime 总预算；旧 KV／GDN 独立硬配额同时出现时报冲突。原模式保留原语义。 |
| 启用方式 | 首版通过总预算参数显式启用，完整压力报告后再讨论默认推广。 |
| 执行范围 | 文本 serving，覆盖现有 TP 运行路径；每卡独立物理池、统一请求暂停／恢复。不新增原本不支持的 TP-SD；多模态暂不纳入共享模式。 |
| 物理实现 | VMM共享物理块；KV保留attention布局，GDN／Replay按槽／行集中各层，完成必要内核适配。 |
| 压力服务顺序 | 优先让最早到达的请求完成，从较新请求暂停；不采用时间片反复换入换出。 |
| 上下文能力 | 显式最大上下文超出单请求可执行容量时启动报错；未指定时自动推导并公布。 |
| 并发上限 | 默认由资源／执行能力自动推导，手动值仅作额外上限；取较小值并报告，不按该数预占GDN／Replay数据。 |
| 分配控制 | CPU决定块归属和安全回收；GPU负责slot_mapping、表更新和计算寻址。首版不实现GPU自主全局分配器，VMM物理共享保留。 |

启动时预分配总容量并不需要预知并发。要消除的是不可互借的固定份额，而非所有预分配。KV 和状态的数学、dtype、前缀隔离、SD 接受规则不因共用存储改变。

上述决定不重复征询。下文给出具体算法和所有权；源码审查不能替代实现后的GPU正确性、开销及持续服务验收。

## 2. 当前约束与必须改变的点

| 现状 | 本次变化 |
|---|---|
| `linear_state_pool._default_pool_slots` 按最大并发倍数预留；Replay 记录也按上限物理分配 | 逻辑请求上限只限制调度／元数据，真实状态与记录随活跃请求分配。 |
| KV、GDN、DFlash 各建独立 GPU 张量 | 保留组件视图和索引语义，物理块来自同一所有者。 |
| prefill 准入按未缓存输入＋完整 `max_tokens` 扣额度 | 按本次 prefill／恢复和后续最小推进需求准入；上限是终止条件，不是每请求的全程预留。 |
| 冷前缀被淘汰后，只返还本类型页／槽 | 最后一个使用者释放且在途工作结束后，空物理块可改供另一类型使用。 |
| 只有空闲重建才能改变池容量 | 总 runtime 容量不变时可以在线改变内部用途，无需全局重建／重录 Graph。 |

不能把现有 tensor 换个名字后仍全量分配，也不能让每次 decode 都执行 CUDA 分配／取消映射。主线组件入口见 `scheduler/cache.py`、`kvcache/{mha_pool,linear_state_pool,gdn_replay}.py`、`speculative/dflash_cache.py`、`scheduler/host_tier.py`。

## 3. 公开配置

- 新增一个容量参数 `--runtime-cache-gib R`，Python使用`runtime_cache_gib`；R为正数，表示每个GPU worker的容量，0不是关闭方式。省略／Python的None保持原模式，不再新增启用开关。TP总runtime预算为各worker容量之和，不能把两张卡的空闲字节当成一张卡可用。
- 共享模式与显式 `--num-pages`／`--num-tokens`／`--gdn-state-budget-bytes`、显式状态缓存份额及仅用于旧分池的 `--kv-reserve-tokens` 冲突。内置旧默认不能被误判为用户显式配置；共享路径不应用旧分池公式。
- `--max-seq-len-override` 是请求长度上限，不是 KV 池预分配量。`--max-running-requests` 是可同时执行的数量上限，不是预期并发；显式值仍有效，不按该值预留完整 GDN／Replay 数据。
- 共享模式的实际并发上限按第5节推导；手动值只是额外限制，实际取较小值并报告请求值和生效值。实际准入仍按当时占用决定，不写死为4用户，也不承诺上限内所有长请求同时驻留。
- 专家显式配置保持原值。专家自动配置时先扣明确的 R 与固定工作区，剩余按现有专家规则分配；放不下即报错，不偷偷缩 R 或显式专家池。
- 复用 `--prefix-cache-host-gib` 的单个 CPU 预算存放冷前缀及暂停请求快照；不新增第二个 CPU 数据池。0 表示不存这些副本，压力恢复使用已批准的重算路径。CPU 输入 token／请求元数据另按现有请求生命周期保留并报告。
- 明确请求共享模式但硬件／组件不支持，应在 ready 前报具体能力错误；原模式仍可用。不得悄悄退成旧分池后报告共享已生效。

首版共享服务收到多模态请求时明确返回不支持该请求类型，不仅靠模型名限制；其原有非共享运行路径保持。单GPU和现有TP的能力校验分别执行，shared runtime本身不能新增全局`tp_size==1`限制。

普通 HTTP／SSE 不增加客户端调度参数。暂停不是请求失败，不重新发起请求；现有取消、超时、stop、EOS、输出上限继续有效。

CLI `--max-running-requests`对应既有Python／配置字段`max_running_req`。入口须保留“未指定”和“显式给值”的区别：共享模式未指定才自动推导，原模式未指定仍沿用原默认；不能因用户显式值恰好等于旧默认就把它当作省略。旧分池配额的显式性同样在进入预算解析前保留，不由热路径猜测。

## 4. 预算和物理存储

GPU 总占用拆成：固定模型／drafter 权重＋专家池＋runtime 物理容量 R＋明确的执行余量。DFlash 权重不再记到 GDN 名下。Graph、注意力工作区和受批次预算限制的临时激活由执行余量支付；分层保留特征／中间状态必须纳入波次准入的峰值，不能隐身在缓存预算之外。本次不重写全部 PyTorch 算子的输出分配。

runtime 内分别统计活跃历史、可回收前缀、SD 暂存、在途复制保护、块内空隙与可复用空块。逻辑槽空闲不等于物理块已空；虚拟地址范围不算显存。保留在 allocator 中的空物理块仍计入 R，不以驱动空闲显存作为唯一的共享证据。

启动时取得总量不超过R的物理块，初始作为公共空块，而非按组件瓜分；运行时按需建立映射。其他进程不能占走已取得的runtime块，但这不等于保证共享设备上的算力或额外工作区永不受干扰。粒度向下取整后的有效容量明确报告；固定执行余量另留。不是为每种用途都申请一份R，也不通过每token的`cuMemCreate`维持分配。

### 4.1 已选实现：稳定地址、按块映射

采用CUDA虚拟内存管理（VMM）：保留稳定地址范围，真实GPU内存按块映射进去，释放的块可以改供另一组件。KV保留现有布局；GDN／Replay改变外层存储顺序，内核按实际槽／行stride寻址。具体布局、2 MiB粒度分析、两处FLA修改及其他内核接入见[内核实施协议](runtime-pool-kernel-design.md)。不采用逐轮整池打包复制。

CUDA 支持分离地址预留与物理分配，以及按粒度映射、撤销映射；PyTorch Graph 回放要求所用地址保持有效。这支持上述设计方向，但**不能替代本项目的兼容性与开销验证**。[CUDA VMM](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/virtual-memory-management.html)、[PyTorch CUDA Graph](https://docs.pytorch.org/docs/main/notes/cuda.html#cuda-graphs)。

约束如下：

- 查询设备支持与最小分配粒度；不硬编码某张卡的粒度。一个可独立返还的块必须是独立映射单元，不能先映射整池再假设能任意切掉一部分。
- 各组件的地址容量从 R 与已声明的形状上限推导，仅预留虚拟地址；实际映射按单位需求执行。多个逻辑槽可能落在同一物理块，块必须等所有槽及在途访问释放才可转用。
- 保留固定 dtype／stride 和 dummy 位置；哨兵物理块计入 R。禁止对包含未映射区域的整个虚拟张量执行 `zeros`、复制或扫描；仅初始化已取得的单位。
- 冷复制、Graph、eager 操作都持有相应块的使用权；相关事件完成后才撤销映射。禁止在还有读取／写入时将同一物理块改给别的用途。
- 新映射按 Driver API 设置可访问性。映射可能同步且存在成本，按批次／块边界合并处理；同类空块优先复用，压力下才跨类型回收，不逐 token 取消映射。
- 原生分配必须独立计入物理占用，不能只看 `torch.cuda.memory_allocated`。张量视图、Graph 与地址所有者的销毁次序明确，正常请求分配不触发 Graph 重录。

上述映射和撤销限制来自 [CUDA Driver API](https://docs.nvidia.com/cuda/cuda-driver-api/cuda_driver_api/group__CUDA__VA.html)。当前三张4090只读查询的最小／推荐粒度均为2 MiB；其他设备仍查询自身能力。真实FI／GDN／Replay／DFlash的Graph回放、粒度浪费和块转换延迟是实施验收项目，不是留待选择的算法分支。

普通GPU大块＋软件地址表方案不实施。若实际证据迫使改变已选架构，应携带失败条件和影响重新讨论，不能以“仅合并统计”或整体eager回退宣称完成。

这里有两层不同映射：请求token位置到KV页／状态槽的映射仍由现有计算接口使用；这些GPU虚拟地址到共享物理块的映射由VMM实现。CPU管理页号与PagedAttention、RadixAttention的控制侧分工相近；Radix树负责前缀查找与共享，不能仅凭一棵统一树就推断不同类型物理池已经互借。[PagedAttention](https://arxiv.org/abs/2309.06180)、[RadixAttention](https://www.lmsys.org/blog/2024-01-17-sglang/)。虚拟／物理内存分离的底层方向与[vAttention](https://arxiv.org/abs/2405.04437)相关，但本方案保留现有paged-attention计算接口，不照搬另一套attention实现。

### 4.2 最小组件接口

一个 runtime 所有者负责物理块与总预算。现有 KV、状态、Replay 和 draft 组件负责自身单位布局，不由 scheduler 索引模型内部张量。

| 职责 | 输入／输出及调用方 |
|---|---|
| 预估本次增量 | 组件根据真实长度／已有绑定给出新增物理块及峰值；准入、恢复、SD 窗口选择共用，计入对齐与块内已有空间。 |
| 取得／释放单位 | 保留页、状态槽、Replay 行的现有逻辑索引；先取得预算再建立映射，释放按最后使用事件返还。 |
| 状态保存／恢复 | 组件提供已提交边界的可恢复内容，继续使用现有复制模块；不创建另一套公共前缀树。 |
| 空块回收 | allocator 返回真正能转用的块，而不是把所有可淘汰 token 字节直接当成可用显存。 |

常规分配失败不得留下半套目标／draft／状态绑定。用请求轮次现有所有者清理已取得资源，不为此建设通用事务框架。

共享路径不再把KV和GDN的各自`available_size`当成两份独立额度。一次准入／恢复／SD轮次形成一个联合申请记录：锁定所需已有历史→选逻辑单位→计算未映射块增量→取得物理额度→建立映射和初始化→各rank确认→提交计算。预期不足在提交前退出并撤回该记录；已在途的单位不计作立即可用。该记录只服务本次操作，不建设任意事务框架。

逻辑单位仍由原组件管理；物理块的使用计数跟随真实分配／最后释放，而非每次前缀引用增减都重复收费。复制或计算仍引用时先进入待回收状态，事件完成后才允许另一组件使用。

空闲逻辑槽数只表示可用编号，不等于能取得物理空间。共享模式的`ensure`路径按联合物理额度回收；可选前缀快照不能优先于本轮必要推进。公共内容仍按已有前缀策略和组件引用条件淘汰，不因为需要GDN就只能淘汰GDN，也不破坏部分组件仍在使用的节点。

CPU维护块归属、引用和绑定元数据，调用Driver VMM接口建立或解除物理映射；GPU根据块ID、请求位置和有效长度生成slot_mapping，批量更新页表／full→window表，并在计算时查表。CPU只提交分配变更和必要批次描述符，不逐token生成完整地址，也不回读GPU空闲队列来决定本轮VMM映射。

请求和前缀节点保留CPU可追踪的索引载荷，复用同一棵树负责分裂、共享、锁和淘汰；不复制KV数据来做管理。首版不增加GPU自主全局分配／回收、设备侧发起新物理块申请或CPU/GPU共同决定块所有权的协议。这个范围边界不取消VMM、必要的GPU映射kernel、暂停恢复或完整验收。具体接点见[前置功能对齐](runtime-pool-integration.md)。

## 5. 准入和保证推进

### 已知信息与容量上限

准入只使用：当前输入长度、已有缓存、已提交输出、实际占用、在途操作、本轮执行形状，以及模型／请求声明的长度上限。它不读取 trace 后续请求或预测真实结束位置。

计算单条请求在独占 runtime 时可支持的长度：目标历史＋启用的必要draft历史＋一个活跃GDN／Replay状态＋最小AR推进余量，包含真实块对齐、dummy和恢复峰值。显式最大上下文放不下时启动报错；未指定时取模型上限内可执行的最大值并公布。请求到达后按这个公开上限处理长度错误／输出截断，不能接收后无限暂停。该上限不是为每条请求保留整个输出空间，本次不实现CPU流式超长attention。

### 启动时的确定性容量推导

设 `G` 为设备映射粒度，`R_eff=G*floor(R/G)`；`E` 为沿用引擎总预算策略留下的执行／元数据额度。所有计算按TP本地shape进行，最后取得各rank都可用的范围。

- `blocks(plan)`：把计划包含的有效字节区间按G取整，对每个地址区间去重后求和；运行时增量还减去已映射块。GDN、Replay、KV、draft和dummy都从其真实视图布局生成区间，不能只将逻辑bytes/token相乘。
- `single(L)`：单请求在合法紧凑位置持有L历史、必要状态和下一次AR／恢复操作时的物理峰值。按 `single(L) <= R_eff` 与单请求执行开销 `<= E` 求出上下文上限；包括prefill分块和重算的峰值，不假设未来提前EOS。
- `live(C)`：C个活跃请求各自最小状态／记录／推进空间的物理下界，包含常驻dummy。它只用于限制可能的执行人数，不用于预分配这些状态。
- `exec(C,L,Q,N,graphs)`：请求表、索引、真实／padding行缓冲、Graph固定区和合法单次计算工作区的上界；Q为prefill上限，N为配置草稿上限。描述符沿用内核协议的有界共享方式，不能留下DFlash的逐batch重复索引分配。

先确定L，再求满足 `live(C) <= R_eff`、`exec(...) <= E` 及组件形状／寻址边界的最大C。若有手动并发上限，生效值为两者较小者。整数边界计算不运行工作负载、不做吞吐调优或完成时间预测；界面同时报告资源上限和手动上限。一次实际batch能否使用SD仍由本轮额外状态和窗口峰值决定。

C是可执行的容量上限，不是推荐的最快batch。运行时不把runtime空块自动送给专家池，也不因专家容量占比低于某个比例自行切换调度或SD；性能选择仍由现有独立配置表达。本feature的收益是减少分池闲置与压力下的重算／失败，不承诺CPU专家受限的负载在更大并发下更快。

这里的工作区计算包含真实图padding尺寸、已配置的草稿上限和允许同时在途的缓冲。`max_extend_tokens`是prefill上限，实际tile可以更小；其物理padding与状态保留峰值一起计价，不能用当前很短的请求推断后续大tile也能放下。至少一个合法最小tile和一次AR都必须可执行。

上述字节描述由真正创建缓冲的组件提供，同一结果用于启动、准入、维护和统计；模型／backend负责自己实际的padding、dtype和workspace，scheduler不复制模型名分支。Graph初始化实际开销纳入ready前总账；自动C可以在预算内收敛，不能通过缩R／显式专家池掩盖超额。不存在一个能执行的C时明确失败。

### 执行余量必须保证已准入工作可完成

历史真实trace在layered＋DFlash的后续prefill发生运行期OOM。本轮确认共享模式不能将启动实测tile容量外推成更大的保留波次；已按实测容量限制波次，并完成原58请求，详见[收尾报告](runtime-pool-closeout.md)。原`PrefillMemoryBudget`的历史测量和“至少一个配置tile”兜底不是容量保证。共享模式按同时存活的波次状态、GDN临时结果、草稿／验证缓冲和Graph padding计峰值；放不下配置tile就缩小实际tile／波次，不能强行放行或OOM后重试。

波次开启时取得到安全边界所需的R与E，后续decode／SD不能侵占；未完成状态不能因压力直接卸载。R内空物理块仍计入R，不自动变成PyTorch workspace；Graph捕获新增reserved量也不等于Graph全部占用。具体接入及已知负载见[实现交接第6节](runtime-pool-integration.md#6-实现agent必须完成的接入)。

### 每轮流程

1. 提交已完成输出，处理取消，结清复制和资源回收。
2. 为已有请求本轮的 AR／prefill 推进计入峰值；为恢复请求同时计入目的页、状态与恢复工作区。只有逻辑可淘汰量而物理块尚未释放时，不先花掉这份额度。
3. 余量允许再取得 SD 暂存。legacy／波次外可按请求缩短；波次内保持整批满配置窗口，否则本轮整批AR。不改配置最大步数，不借资源裁剪新增波次内可变宽度调度。
4. 余量允许才接纳新请求。它不能占用已经安排的推进／恢复额度。部分 prefill、共享前缀和 DFlash 上下文均按真实本轮工作计价。
5. 不足时先回收无保护冷缓存，再缩短 SD、停止新准入；仍不足才暂停活跃请求。控制器已经选择 AR 时不为未执行的草稿回收缓存。

降低 SD 资源与冷缓存回收不需要求解器。二者具体执行顺序可合并到一次容量重算，不能启动昂贵备份阻塞本可继续的 AR。

### 已确认的压力服务规则

按scheduler接收请求的顺序优先保证最早的未完成请求继续，从较新的请求开始暂停，直至本轮可执行。到达顺序在首次进入时确定，恢复不重置；TP由同一接收顺序决定。新到达者不能抢走这个推进机会，不按预测剩余长度、接受率或未来成本排序。

一轮压力处理后，不立刻把刚暂停者恢复回来；至少等当前受保护请求完成／取消，再按原始等待顺序重新准入。极端压力下可以退化为逐条完成。每条合法请求的长度有界时，这提供有限队列下的推进依据，但不承诺过载下固定尾延迟。

已发出的计算／复制先到安全边界。若layered波次中的状态尚未跨全部层一致，可以先完成已取得资源的有界波次再暂停；此时暂缓其他无法取得新页的decode，而非导出半完成状态。压力时不扩张该波次，所需峰值必须在准入时已经计入。

共享前缀会使暂停一条请求释放很少空间，回收量以最后引用释放后的物理块为准。如果其余请求均暂停后仍因碎片无法容纳单条请求，使用已批准的卸载／重算在空池中紧凑恢复；不能无限反复换受害者。单请求可执行边界必须把这一恢复峰值算进去。

## 6. 暂停、卸载和重算

### 6.1 请求状态

```text
等待 -> 运行 -> 正在保存 -> 已暂停（CPU快照 或 可重算）
已暂停 -> 等待准入 -> 恢复/重算 -> 运行
任意阶段 -> 取消/结束 -> 等待在途引用结束 -> 资源释放
```

请求身份、原始到达顺序与 SSE 连接不变。GPU 表行可以释放并在恢复时重新分配，不能把 table_idx 当成请求身份。状态转移放在现有请求所有者中，不另建第二个 scheduler。

待恢复／重算请求以及在途复制都纳入调度的可运行判断；即使没有任何新HTTP请求到达，也必须推进完成回调和恢复，不能全员暂停后阻塞在接收新消息上。没有可执行工作时沿用等待／poll机制，避免忙循环。

### 6.2 必须保存的两个边界

- **已提交输出边界**：哪些 token 已经确定并交给原有输出路径，连同 stop／EOS／usage／detokenizer 的现有状态。
- **模型状态边界**：KV／GDN／draft 历史实际计算到的位置，以及已确定但尚待下一次模型计算的输入尾部。

普通 decode 中二者通常相差一个 token，SD 中必须在最终保留长度提交后确定；不能用一个长度替代二者。保存包括输入和已提交输出 token、采样参数、组件位置及已有前缀引用。未接受草稿不保存为历史。

保存的是原始token记录，不从已发送的文本重新tokenize。未prefill的原始prompt也必须保留，不能只保存`ChunkedReq`当前已处理的前缀；输出上限、原prompt长度和已生成数量不因暂停重新起算。

### 6.3 暂停顺序

1. 停止向该请求提交新轮次，结清已经发出的计算与输出；不打断内核，不在半轮验证中保存。
2. GDN／Replay 通过现有组件能力将状态物化到模型状态边界；完整状态快照可代替此前的 Replay 记录。起草暂存释放。
3. layered prefill 只在所有相关层一致的 token 边界暂停。进行中的有界 tile／波次先走完已取得资源的安全边界；不能将半层 hidden 当完整 KV 备份。
4. 尝试从现有 HostStore 取得空间；先淘汰普通冷副本。保存目标历史、状态以及 draft 所需完整历史／窗口；可复用的 HostSpan 保持共享引用。
5. 保存完成后才解除 GPU 引用并返还真正空的物理块。CPU 空间为0／不足时转为可重算状态，保留恢复输入与提交边界，释放 GPU 内容。

CPU 保存／恢复共用现有预算和复制队列。暂停请求的完整副本在仍标记为 CPU 恢复时不可被普通冷缓存淘汰；若需回收，先明确转成可重算状态。取消正在复制的请求，待复制结束再释放引用，不要求取消已提交 DMA。

缓存管理器只持有一份HostStore／复制队列供公共冷缓存和私有暂停记录使用。`cache_type=naive`也必须可以暂停／恢复：不因没有公共前缀树而禁止私有CPU保存，也不偷偷开启前缀复用。GDN活跃槽与请求表行解耦，不能仅在`state_cache`开启时才分配；关闭前缀缓存不等于没有GDN状态。

暂停记录由请求自己持有，不冒充请求完成，不调用会结束请求的资源释放出口，也不强行作为OUTPUT前缀发布。已经存在的公共前缀可以共享；保存完成后应解除该请求的GPU保护，否则“已卸载”仍无法返还物理块。每轮可以丢弃的SD草稿和可选快照不能挤占保存／继续所需的最小空间。

### 6.4 恢复与重算

- 恢复前一次计价必要目的空间与本轮推进量；不能先恢复一半再发现永远没有空间继续。
- CPU 恢复完成并发布全部必要组件后才运行；Replay 可从物化 checkpoint 重新建立空记录。保留目标与 draft 的一致位置，绝对位置不重置。
- 重算从可用的合法前缀开始，用保留的输入和已提交输出重建到模型状态边界；不调用输出采样，不重发旧 SSE，不重复增加 usage，也不重复执行工具调用。
- 重算产生的真实计算量单独报告，不能冒充新用户 token 或新增缓存命中。完成后从保留的未计算尾部接着生成。
- 首次TTFT起点和已发送token的时刻不重置，恢复不会重复发送prompt准入通知；已有prompt的`cached_tokens`不因恢复生成历史而增加。
- CPU 副本按存储 dtype 无损搬运；重算可能有不同执行计划的浮点差异，沿用主线数值政策。不新增“随机采样与从未暂停逐字一致”的承诺；恢复不得重置请求参数或重新抽取已提交 token。

首版只覆盖文本请求。不能仅用多模态 token id 重算视觉输入；后续纳入时必须同时保留可重放的原始输入／特征及其预算。

### 6.5 TP：本地存储，统一决定

现有请求广播见 `scheduler/io.py`；layered准入已有跨rank取最小可执行token预算，冷复制的poll/drain也已有TP完成确认。复用现有CPU通信组和请求顺序，不增加第二套分布式调度器。

1. 各rank根据本地组件布局、占用、映射粒度计算同一候选轮次是否可行；共同选择都能执行的请求集、长度和阶段。比较可行工作量，不把不同rank的剩余字节相加，不用启动时最大空闲量替代最弱rank的限制。
2. rank0统一确定暂停UID及恢复顺序并广播。各rank对同一请求使用相同提交边界，物理地址／块编号可以不同。完成约定前没有rank进入下一轮模型collective。
3. 所有rank都取得本轮所需资源后才提交forward。预期容量失败先释放该计划已取得的未使用资源，再共同降SD长度／暂停；不能只有一张卡直接AR、重算或跳过请求。
4. CPU快照保存方式也需一致：任何rank无法保留所需CPU数据时，该请求整体转重算。复制完成取所有rank均完成，各rank不得按自己DMA先完成便提前恢复。
5. 对新映射／分配的结果在模型collective之前作成功确认。真正CUDA错误按现有worker失败机制向外报告，不伪装成容量不足，也不要求新建跨进程容灾恢复框架。
6. 低成本容量／就绪信息放在一致的调度边界，尽量复用一次紧凑控制交换；每rank都进入同序通信，不能只在本地内存紧张的条件分支调用。无需每个组件／层增加barrier。

每张GPU独立模型的多实例不属于TP：各自使用自己的预算与调度即可。本功能不建立全机调度器。

共享模式以逐rank预算是否可满足为准，不沿用旧自动KV几何所需的“空闲显存差超过固定阈值就拒绝”作为额外限制。每卡都能满足明确R及其固定资源才ready；任一卡不足则共同失败并报告。原分池模式不借本次改动改变其行为。

## 7. 与其他功能的边界

- 以已整合的SD／DFlash接口为准。[实现交接](runtime-pool-integration.md)记录独立预算、分层features、窗口映射、capture hooks及内存账；旧分支差异已经收口，不重新移植一套执行／缓存流程。
- batching 和 SD 开关继续独立。shared runtime 不强制 SD；`steps=0` 没有 SD 数据分配。启用 SD 后因一轮容量不足使用 AR，只改变本轮执行，不热卸载草稿模型。
- 阶段策略／自适应暂时选择AR时，DFlash上下文仍维护，供后续SD继续使用；这与显式关闭SD不同。共享模式用联合预算检查最小合法SD轮次，不能继续用旧GDN分区余额决定是否支持SD。
- DFlash 主线的全历史／窗口分组、渐进解锁继续生效；窗口真实分配从 runtime 获取，不能仍按最大并发先占满窗口池。无限历史也不能一启动就映射目标总容量的另一整份。
- GDN 前缀快照按实际保留与回收管理；不再以并发倍数给其固定份额。公共前缀的 cache_group、引用和复制完成语义保持。
- 改 runtime 内部用途不调用空闲重建；改变总 R、专家容量或虚拟地址几何仍走显式维护流程。暂停请求也算未完成请求，不能把它们当成空闲直接清掉。
- 总预算重建失败的公开语义沿用主线。扩容不能突破原总 GPU 预算或暗中缩专家池。无需新增在线更换模型／drafter的接口。
- 主线公开维护接口尚不支持的TP总池重建，本次仍明确返回unsupported；TP正常运行中的内部容量转用与请求暂停恢复不依赖该接口。单GPU共享模式的重建使用同一个runtime总预算字段，旧分池重建字段报冲突。公共缓存清理不删除仍被暂停请求持有的私有恢复副本。
- DFlash固定SD覆盖layered的outwave／inwave／all及offload／hybrid；自适应默认关闭，仅保留现有legacy／后端支持，不扩展layered自适应或重做其策略优化。当前单个有限窗口组按最大窗口实际计价，独立窗口组优化另行交付。共享runtime保留这些边界，窗口优化＋layered固定SD必须验收。

单GPU维护入口沿用`POST /v1/cache/rebuild`与`mode=if_idle`。已启用共享模式时，新增请求字段`runtime_cache_gib`表示新的总预算；`moe_cache_size`仍可显式维护，省略时不得自动改变专家容量。`num_pages`、`num_mamba_slots`、`num_swa_pages`和`swa_full_tokens_ratio`属于旧分池维护字段，在共享模式明确拒绝。省略所有有效容量变更时沿用原接口行为；不通过此接口热切共享／非共享模式。暂停或正在保存／恢复的请求仍使维护返回busy；非法／不合预算的申请在拆旧资源前拒绝。

## 8. 状态和验收

在既有 stats/cache status 中增加共享 runtime 的实际模式、总物理预算／持有量／空块量、各用途占用、块内浪费、在途保护、暂停／恢复／重算次数与 token 数、等待时间、映射次数／耗时及内存不足原因。旧“KV总token容量”“GDN总槽数”若仅表示虚拟寻址上限，必须改标语义，不能继续作为可同时使用的物理容量报告。

验收见[独立公开契约](runtime-pool-public-contract.md)。独立测试作者只拿公开契约与运行配置，不读本文、内核实施协议、生产源码、diff或实现笔记；本设计不编写测试。源码核对只覆盖设计依据，不代替独立验收。

核心证据是同一进程、同一 R 内完成“多短请求状态占用上升→请求结束→少量长上下文 KV 占用上升”，无需重建；反向也成立。还须覆盖 CPU 满／关闭、反复压力、冷恢复、取消、SD／AR、Graph及混合长度。不能只用显存曲线下降或 HTTP 成功证明物理共享与完整恢复。

TP验收覆盖现有可运行的分片模型与组件、各rank就绪时间不同、公共预算压力、暂停后取消、CPU不足转重算及持续forward；检查没有rank提前进入不匹配的collective。TP-SD仍按该组合原有能力判定，不把新增TP-SD算作本功能要求。

性能以完整请求吞吐、TTFT、TPOT和最长输出间隔报告；另列暂停、复制、重算、映射开销。使用持续到达、突发和负载阶段变化，同一服务不按每个场景重启调池；没有通用加速承诺或未确认的固定百分比门槛。

已知长历史＋后续prefill OOM场景列入共享模式回归：保持真实请求、专家池和总GPU预算，用R替换旧分池硬配额；允许本设计的动态准入／tile／暂停，不以缩短输入或关闭SD代替完成。原分池模式的旧缺陷与共享模式结果分别报告，不能宣称本轮文档已修复运行问题。

关键设计决策已在本轮确认，不再将内核方案、压力顺序或容量接口留作实现时任选。若实际失败证据要求改变已确认架构／支持范围／预算或默认行为，再携具体影响讨论；常规修复继续在本协议内完成。性能数值必须由实际完整请求报告给出，不能靠设计讨论承诺尚未测得的加速。
